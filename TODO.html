midi_mover Implementation Backlog

This document is the single source of implementation instructions for a later coding agent. It contains the required scope, architecture guidance, epics, tasks, subtasks, definitions of done, and workflow rules. Do not assume hidden requirements outside this page.

All items start as TODO. When a subtask is fully complete, change its label to DONE. If all subtasks in a task are done, set the task to DONE. If all tasks in an epic are done, set the epic to DONE.

Global product definition

  • Build a single-player rhythm game called midi_mover.
  • Use a two-stage Ultralytics pipeline: stage 1 body/pose detection for person + eye anchors, and stage 2 hand-keypoint detection on a person-ROI crop. Do not build separate custom detectors outside Ultralytics models.
  • Head center is the midpoint between the two eye keypoints.
  • Gameplay interaction events must be driven by fingertips from the hand-keypoint model, not by wrist keypoints from the body model.
  • The gameplay screen is split into 60% live camera view on the left and 40% note timeline on the right.
  • The live camera view must crop around the player, stretch to full panel height while preserving aspect ratio, and pad left/right as needed to fill the panel width.
  • There are 5 circles around the head. Their fixed semantic numbering is: 1 = far left, 2 = upper-left, 3 = above head, 4 = upper-right, 5 = far right.
  • Gameplay notes are tokens L1..L5 and R1..R5. L means left hand must enter the circle. R means right hand must enter the circle.
  • Target songs are loaded from a folder of MIDI files. On startup, choose a random MIDI. After each song, choose another random MIDI.
  • Audio quality is a first-class gameplay requirement: target-song playback should support expressive, high-quality instrument timbres (not only basic beeps/sine cues).
  • The right panel is a Guitar-Hero-like waterfall timeline with 5 vertical lanes. Notes move from top to bottom. The horizontal “now” line is fixed at 25% of panel height from the top.
  • After notes are judged, they remain visible below the now line and are colored green on hit and red on miss.
  • Show the MIDI-derived song title before starting each song. The title is extracted from the MIDI filename, not from MIDI metadata.
  • At the end of every song, show result summary and the highscore board. If the result qualifies for a new highscore entry, show a countdown from 3 to 0, take a new headshot, save it, and show the updated board.
  • The highscore board must always show score and percentage of notes hit, even when the just-finished run is not a new entry.

  • Always fulfill each subtask completely before moving to the next one.
  • Use the conda environment midi_mover.
  • After each completed subtask, the complete pipeline must run. “Complete pipeline” means the app must launch, load config, open the camera, initialize the window, load at least one MIDI file, render the liveview/timeline composition, and exit cleanly without regressions. Use a minimal smoke-test path if the full interactive flow is not practical in automated mode.
  • After fulfilling a subtask, update this TODO.html file immediately and set that subtask to DONE.
  • If all subtasks under a task are done, set the task to DONE.
  • If all tasks under an epic are done, set the epic to DONE.
  • Do not use git. Do not create commits, branches, tags, or Git metadata.
  • Keep the project runnable from one explicit entry point, for example:

  • Do not hardcode magic numbers in source files. All tuneable values must live in a YAML config file.

Configuration requirement: all hyperparameters must live in YAML

Create a dedicated YAML configuration file, for example config/default.yaml, and load it at startup. The later agent may add more keys, but at minimum the YAML must own all tuneable values from the list below.

Application and runtime

  • window width, height, target FPS
  • debug flags
  • logging level
  • random seed behavior

Camera and pose

  • camera width, height, mirror on/off
  • Ultralytics stage-1 model path/name
  • Ultralytics stage-2 hand-keypoint model path/name
  • pose confidence threshold
  • IOU threshold
  • device selection (CPU/GPU)
  • stage-2 ROI expansion in pixels around detected person bbox (default 30px each side)
  • tracking smoothing factors
  • lost-person timeout and fallback behavior

Liveview layout and circles

  • left/right panel ratio
  • crop margins around person
  • circle radius
  • circle offsets relative to head center
  • circle stroke width
  • label font sizes
  • padding color

Gameplay and judgment

  • hit window in milliseconds
  • early/late tolerance
  • debounce timing for fingertip-in-circle events
  • fingertip trigger policy (which fingertips can trigger, per-hand/per-finger options)
  • note history duration below the now line
  • lookahead duration above the now line
  • score values, combo bonuses, miss penalties
  • debug overlays for full keypoint rendering from stage-1 and stage-2 models

MIDI and mapping

  • supported MIDI extensions
  • note-number to gesture-token mapping
  • optional dynamic/adaptive note-to-circle mapping mode
  • rolling note-history buffer size for adaptive mapping (for example last 30 notes)
  • track/channel filtering rules
  • minimum note duration thresholds
  • ignored meta events and unsupported-note policy

Audio, summary, and highscore

  • audio backend selection (pygame or pyfluidsynth)
  • backend-specific low-latency settings (buffer, sample rate, channels)
  • SoundFont (.sf2) path and loading policy for FluidSynth
  • MIDI channel/program handling and optional instrument override profiles
  • FluidSynth mix controls: gain, polyphony, reverb, chorus
  • volumes for cue, hit, and UI sounds; plus target-song playback gain
  • fallback audio behavior when preferred backend is unavailable
  • highscore list size
  • headshot countdown duration
  • headshot crop margins
  • thumbnail dimensions

Rule: if a later agent needs to tune something during implementation, that value must be moved into YAML instead of being left inline in code.

Assumptions that the later agent must preserve

  • Single visible player only. If multiple people appear, pick one primary person consistently and ignore the others.
  • The camera ID and MIDI folder path are external inputs, not hardcoded.
  • MIDI parsing is done with mido.
  • Audio playback uses a pluggable backend. Preferred target-song renderer is pyfluidsynth (SoundFont-based), with pygame retained as a compatibility fallback.
  • Runtime window rendering is done with pygame.
  • The live camera stream can be processed with OpenCV and then blitted into pygame surfaces.
  • All note-to-gesture mapping must be configurable in YAML. The implementation must not assume arbitrary MIDI files are naturally playable without mapping.
